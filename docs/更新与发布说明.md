# BallNote 更新与发布说明

本文说明 BallNote 的应用内更新机制、GitHub Actions 云端发版流程，以及用户笔记数据的保护与恢复方法。

## 1. 方案概览

更新系统使用标准组合：

```text
GitHub Actions
+ electron-builder
+ GitHub Releases
+ electron-updater
+ NSIS
```

发布链路：

```text
推送 tag（v0.1.1）
  → GitHub Actions 在 windows-latest 构建
  → electron-builder 生成 NSIS 安装包、latest.yml、.blockmap
  → 自动创建/更新 GitHub Release 并上传资产
  → 已安装的 BallNote 通过 electron-updater 检查并下载更新
```

Windows 安装包仍是 `.exe`，但更新过程并不是应用自行下载后手工覆盖文件。`electron-updater` 会读取 Release 的 `latest.yml`，执行更新元数据解析、文件校验、下载与缓存处理；`.blockmap` 可让后续更新使用差分下载。下载完成后，NSIS 负责标准的替换与重启流程。

## 2. 用户端更新流程

用户在应用中打开：

```text
悬浮球菜单 → 设置 → 系统设置 → 软件更新
```

当前策略是：

```text
后台自动检查（可关闭）
+ 用户手动下载
+ 用户手动确认“安装并重启”
```

具体行为：

1. 用户可勾选“后台自动检查更新”。打包安装版会在启动约 30 秒后检查一次，之后每 24 小时检查一次。
2. 用户也可以随时点击“检查更新”。
3. 发现新版本后，页面显示版本号、更新说明和“下载更新”按钮。
4. 用户点击“下载更新”后显示进度；不会自动占用流量下载。
5. 下载完成后显示“安装并重启”。
6. 用户点击安装前，应用先创建数据备份；备份成功后才调用 NSIS 更新并重启。

开发模式（`npm run dev` / `npx electron .`）不会真的检查更新，设置页会提示需要在已安装的正式版中测试更新。

## 3. 数据保护

### 3.1 固定用户数据目录

用户数据根目录固定为：

```text
%APPDATA%/ball-re/
```

即使应用产品名从 BallWork 改为 BallNote，更新后的应用也继续使用上述路径，不会因为 Electron 默认随 `productName` 变更的 userData 目录而创建空书库。

核心数据包括：

```text
%APPDATA%/ball-re/config/books.json        书籍、章节、笔记
%APPDATA%/ball-re/config/thoughts.json     闪念
%APPDATA%/ball-re/config/calendar.json     日历和回顾记录
%APPDATA%/ball-re/config/note-drafts.json  未保存笔记草稿
%APPDATA%/ball-re/config/folders.json      文件夹
%APPDATA%/ball-re/config/ai.json           AI 设置
```

安装/更新程序替换的是安装目录内的程序文件；不修改 `%APPDATA%/ball-re/`。

### 3.2 更新前自动备份

点击“安装并重启”时，应用会先复制整个：

```text
%APPDATA%/ball-re/config/
```

到：

```text
%APPDATA%/ball-re/backups/pre-update-时间戳/config/
```

例如：

```text
%APPDATA%/ball-re/backups/pre-update-2026-08-26T13-29-06-000Z/config/
```

规则：

- 每次安装更新前创建一份备份；
- 仅保留最近 **2** 份更新前备份；
- 创建第三份时，自动删除最旧的一份；
- 备份失败时，应用取消安装更新并显示错误，不会在没有恢复点的情况下继续更新；
- 为避免每次升级重复复制大文件，备份范围是 `config/`（用户可编辑的 JSON 数据和草稿），不包括可由这些数据重建的 `books/` 目录镜像，也不包括图片资产。

### 3.3 卸载保护

NSIS 配置中明确设置：

```json
{
  "deleteAppDataOnUninstall": false
}
```

因此即使用户卸载 BallNote，`%APPDATA%/ball-re/` 默认保留。重新安装后仍可读取原笔记数据。

> 若将来需要“彻底删除全部本地数据”，应在应用设置中提供单独的危险操作和二次确认，而不是由卸载程序删除。

### 3.4 手动恢复

若升级后发现数据异常：

1. 不要继续新建或编辑笔记，避免新的保存覆盖异常状态；
2. 退出 BallNote；
3. 找到最近的：

   ```text
   %APPDATA%/ball-re/backups/pre-update-*/config/
   ```

4. 复制其中的全部文件，覆盖：

   ```text
   %APPDATA%/ball-re/config/
   ```

5. 重新启动 BallNote。

## 4. GitHub 云端发版

工作流文件：

```text
.github/workflows/release-windows.yml
```

触发条件：推送符合下列格式的 tag：

```text
v0.1.0
v0.1.1
v0.2.0
```

工作流会：

1. 在 `windows-latest` 上检出代码；
2. 执行 `npm ci`；
3. 验证 Git tag 和 `package.json` 的 `version` 一致；
4. 执行 `npm run build`；
5. 执行：

   ```text
   npm run dist:win -- --publish always
   ```

6. 创建或更新 GitHub 正式 Release；
7. 上传以下更新资产：

   ```text
   BallNote Setup x.y.z.exe
   latest.yml
   *.blockmap
   ```

8. 额外保存 Actions Artifact 14 天，供排障或临时下载。

工作流使用 GitHub 自动提供的：

```text
secrets.GITHUB_TOKEN
```

不需要自行创建或填写个人 Token。

### 4.1 GitHub 仓库权限

仓库地址固定为：

```text
https://github.com/libaidaidetang/ballnote
```

仓库需要允许工作流创建 Release。若 Actions 报权限错误，进入：

```text
Repository Settings → Actions → General → Workflow permissions
```

选择：

```text
Read and write permissions
```

工作流本身已经声明：

```yaml
permissions:
  contents: write
```

更新器当前访问公开 GitHub Release，因此仓库应保持 Public；私有仓库需要额外设计认证/Token 分发机制。

## 5. 发版操作手册

假设当前线上版本为 `0.1.0`，准备发布 `0.1.1`。

### 5.1 修改版本号

修改 `package.json`：

```json
{
  "version": "0.1.1"
}
```

### 5.2 本地检查并推送代码

```bash
npm run build
git add .
git commit -m "release: v0.1.1"
git push origin main
```

### 5.3 创建并推送 tag

```bash
git tag v0.1.1
git push origin v0.1.1
```

完成后不需要本地打包，也不需要手动上传 `.exe`。GitHub Actions 会自动完成。

### 5.4 检查发布结果

在 GitHub 仓库查看：

```text
Actions → Release Windows
```

工作流成功后，在：

```text
Releases
```

确认存在正式 Release，且包含：

```text
BallNote Setup 0.1.1.exe
latest.yml
*.blockmap
```

Release 必须是正式 Release：

- 不能是 Draft；
- 不能是 Pre-release；
- tag 必须和 `package.json` 版本一致（tag 多一个 `v` 前缀）。

## 6. 首次真实升级验收

首次发布 `v0.1.0` 后，再发布 `v0.1.1` 时，必须使用一台已安装旧版的测试机完成一次端到端验收：

1. 安装 `v0.1.0`；
2. 创建测试书籍、章节笔记、闪念、日历记录和一条未保存草稿；
3. 发布 `v0.1.1`；
4. 在旧版执行：

   ```text
   设置 → 系统设置 → 软件更新 → 检查更新 → 下载更新 → 安装并重启
   ```

5. 升级后确认：
   - 悬浮球能启动；
   - 书籍、章节、笔记正文仍在；
   - 闪念、日历、文件夹仍在；
   - 草稿可恢复；
   - `%APPDATA%/ball-re/backups/` 中生成了新的 `pre-update-*` 备份；
   - GitHub Release 有 `latest.yml` 和 `.blockmap`。

在上述验收通过前，不建议向大量用户推广自动更新。

## 7. 常见问题

### 7.1 检查更新提示“开发模式不检查更新”

正常现象。`electron-updater` 依赖打包后由 electron-builder 生成的 `app-update.yml`，请安装 GitHub Release 中的正式安装包后测试。

### 7.2 检查不到已发布版本

依次检查：

1. Release 是否已 Publish；
2. 是否误标记为 Draft 或 Pre-release；
3. tag 是否高于当前安装版本；
4. tag 是否是 `v0.1.1` 格式；
5. Release 是否包含 `latest.yml`；
6. 仓库是否可公开访问。

### 7.3 更新显示“没有待下载的更新”

通常是当前版本已经是最新版本，或 Release 没有正确生成 `latest.yml`。请查看 GitHub Actions 的构建日志和 Release assets。

### 7.4 本地执行 npm run dist 失败

本项目当前执行环境曾因 electron-builder 下载 Windows 辅助工具时出现：

```text
connect ETIMEDOUT ...:443
```

这属于本地网络/CDN 访问限制。正式发版应推送 tag，由 GitHub Actions 的 `windows-latest` 云端环境打包，避免依赖本机网络条件。
